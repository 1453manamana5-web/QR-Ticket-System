# Choreis — Cross-device Technology / architecture proposal v0.1
Status: proposal for review, not approved production design. Previous spatial recognition code is excluded. Graphite #25282D, overlapping planes mark interpreted as overlapping devices; preview mark is an approximation, original artwork not recovered.
## Existing integration
Repository 1453manamana5-web/QR-Ticket-System, Pages base /QR-Ticket-System/. Counter manager is a Vite entry at reception-app/counter-management/ and management-app/src/CounterManagerApp.tsx; counterAuth.ts verifies current server installation, terminalOwners, terminal approval and admin/subAdmin. Existing rules deny unmatched paths. No Firebase production config, rules or apps changed by this prototype.
## Proposed engine
A versioned allowlisted view descriptor {schemaVersion,viewKind,componentIds,eventId,mode,filters}; no arbitrary HTML, URLs, scripts, tokens or raw data. Registry maps IDs to responsive view components; snapshot sends only explicitly allowed aggregated fields, live prefers authorized source subscriptions or minimal coalesced projections. Separate snapshots from live data. For later guest viewers, narrowly scoped projection only; no full event access, explicit approval required. Initial pilot: approved admin/subAdmin pairs only, event-specific counter station only after separate approval integration. Device roster from existing grants plus opt-in presence, foreground session ID, last server-confirmed heartbeat. Names are labels, never credentials.
Proposed Firestore path events/{eventId}/choreisSessions/{sessionId} with immutable participant UIDs and installation IDs, version, descriptor, offered/active/ended state, capabilities, consent timestamps, lease expiry, revision, ownership epoch. Separate per-participant inbox/index only if rules require; query scopes must match rules (not client filtering). Rules recheck current roles and approvals for every read/write, participant binding, immutable fields, strict allowed fields/types/bounds, server timestamps/request.time expiry, deny default. No production permissions until emulator tests pass. Consider distinct nonpersistent Firestore instance for shared projections; do not rely on clearing existing cached data or promise remote erase of viewed content. Clear visible shared data on revoke, auth loss, expiration, tab hide as appropriate; offline cached snapshots never indicate live freshness. Server confirms writes and target acks separately. Expiration enforced on server and client; physical deletion is separate cleanup (manual/bounded batch on free plan; no assumed TTL service).
## Session UX
Share -> select approved recipient -> send. Defaults: snapshot, view only, 15-minute proposed maximum; optional Live, explicit receiver open. Incoming panel states pending, active, stale, ended. A persistent compact indicator shows participant/content/permission and stop. Upgrade live within same session with recipient notification; Control and Handoff require new explicit confirmation. No QR code with bearer credentials or automatic proximity discovery. Multiple recipients modeled as separate participant grants; revoking one must not affect others. Initial pilot one-to-one.
## Control (future; no implementation)
Only allowlisted app commands; never OS input, arbitrary JS, DOM selectors, or general screen control. Setup/test scope only initially. On-device visible consent with command categories and short lease. One controller at a time, transactional ownership epoch, command id, increasing sequence, expected configuration revision, server-issued expiration, local consent active and foreground/online check immediately before application. No offline command queue. Receiver validates schema/range/state, applies through existing local setter, persists dedup and outcome where possible; ambiguous crash state requires manual review, not automatic retries. Local stop immediately blocks execution; server revoke blocks future accepted operations, in-flight operations may already have executed. Acks contain applied revision and status; no success before target application. Durable history minimal, bounded, access controlled. Production testing must prove no live count/session side effects, no stale/replay/duplicate actions, loss of auth revokes.
## Handoff (future)
Versioned allowlisted draft state (view, filters, selected device, setup draft/progress), excluding auth, media and sensitive raw records. Receiver accepts with own permissions; compare-and-swap owner/epoch, old editor becomes read-only when authority transfers. Offline no takeover; committed operations not replayed; restore read-only on conflict until revalidated. Existing terminal identity handoff is unrelated and must not be repurposed.
## Installation assistant priority
1) structured schematic (normalized line/zone, anonymous boxes or count metrics, test passage outcomes) without image; 2) approved control commands for lines, sensitivity and tests; 3) only if needed consider WebRTC for fully anonymized synthetic/processed video. No raw video network/recording or face identification; prefer full-frame privacy-safe rendering over uncertain face-only mosaics. Pipeline must stop before sending if anonymization unavailable; explicit on-device approval and viewer indicator. School permission and network/iPad testing required; no paid TURN or new subscriptions without approval. Browser suspension/permission means unavailable, never fake availability.
## Reliability / cost
Count locally regardless of session. No extra reads/writes without active usage; coalesce latest changes, propose 1 Hz for diagnostics, counts event-driven with batching, presence 30–60 s foreground only, stale threshold measured. Firestore cache and pending-write metadata distinguish server vs local. Disconnect blocks control; reconnect revalidates participants, expiry, ownership epoch and discards old commands. Measure p50/p95 end-to-end delay, write/read count, CPU/camera fps/count accuracy with and without sharing. Quotas and school Wi-Fi unverified. No paid services.
## Gates
Phase 1: protocol and UI local mock now, then confirm recipient enrollment and retention; server rules emulator and real two-device test before live pilot. Phase 2: real snapshot then Live, read-only; Phase 3: approved narrow Control and Handoff, failure tests; Phase 4: installation assistant and schematic; optional privacy-tested video; Phase 5 performance and interoperability. Luxnora only proposes actions, never bypasses consent.
## Preview
reception-app/public/choreis-preview/ is a single-browser mock with fictitious recipients and values. No external calls, no credentials, no camera, no actual cross-device communications. State machine demonstrates accept, scope, snapshot/live, stale, expiry/revoke, monotonic revisions. Two-minute preview expiry is deliberately shorter than the proposed pilot default. It is not a security boundary. Existing app integration, server rules, actual multi-device tests and production rollout remain pending. Test: node --test choreis-preview.test.mjs.
