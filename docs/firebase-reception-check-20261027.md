## 修正した不具合

- イベントQR認証で日付・開始終了時刻を保存せず、版数と状態を誤った階層に代入していた。ダウンロード済みイベント本体を保存する。
- 別端末で入場後も、出口側が保存時点の未入場状態を使っていた。オンラインでは現在のチケットを取得し、自端末に未同期記録がある場合はその状態を保持する。
- 即時送信・定期送信・再接続送信が競合していた。同じキュー処理へ統一し、保存順で送信する。前段が失敗したチケットの後続処理は追い越させない。端末の時計変更や同時刻の記録も保存順を維持する。
- チケット再取得で未同期の受付状態が上書きされていた。同じIndexedDBトランザクションでキュー・記録を参照し、未同期状態を保持する。イベント破棄でも受付履歴・キューは削除しない。
- 権限解除後の端末を新規登録として上書きして失敗していた。所有者・インストール対応を検証して同じIDで再申請し、管理者が再承認する。再申請の取消も所有者対応を維持する。
- 権限解除ルールで未設定の `receptionApprovalVersion` に直接アクセスしていた。旧データでは既定値0から増分する。
- 別イベントへの切替は受付専用端末を再申請状態へ戻す。管理兼用の所有端末は管理権限を維持し、新イベントの認証画面へ戻す。
- 初期値の「停止」を遠隔停止命令として実行し、読取を止めていた。命令日時のある操作だけを適用し、同じ命令の再受信で結果表示を消さない。権限取消確認時はカメラを停止する。
- 定期確認が毎回全チケットを取得していた。小さい公開情報だけを確認し、版数変更時に一覧を取得する。再公開時は版数も更新し、受付中でも設定・一覧を更新する。
- カメラの非同期終了が次のカメラを停止し得た。起動・終了を直列化し、対象読取領域の映像だけを停止する。
- 受付のService Workerが管理画面HTMLを受付のオフライン起動画面へ保存し得た。管理画面を対象外にしてキャッシュ版を更新した。認証完了がwindow.load後でもWorkerを登録する。
- `tsc --noEmit` は空の参照元設定を検査しており、画面コードの型エラーを見逃していた。両アプリの `tsconfig.app.json` を検査し、管理メニューの未定義クリックイベント参照も修正した。

## 検証範囲

- クライアント・React画面・IndexedDB・カメラ制御・Service Workerの回帰テスト。
- Firestore Emulatorで実クライアントの登録→承認→再申請→取消→再承認、公開→ダウンロード→入場/退場/再入場→再送、451枚取得、イベント削除を検証。
- 再申請境界で匿名/他人UID、無効な所有者・インストール、自己承認、管理権限追加、所有者変更、余分なフィールド、型・文字列長の不正、片方だけの書込を拒否するテストを実施。
- 管理・受付の型チェックと本番ビルド。

新ルールは限定的な変更であり、既存の管理者向け業務データ全体に詳細なスキーマ検証を追加したものではない。本番iPadのカメラ・Safari・PWAでの実機操作は未確認。オフラインで複数端末が同じチケットを処理した場合のサーバー競合や、公開終了後に残った未同期記録は、履歴を保持したまま管理者が確認する必要がある。

I've set up prototype Security Rules to keep the data in Firestore safe. They are designed to be secure for owner-verified reception reapplications that preserve terminal identity and require management approval. However, you should review and verify them before broadly sharing your app. If you'd like, I can help you harden these rules.
