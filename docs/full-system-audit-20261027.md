# 受付・管理アプリ 全体安定性確認（2026-10-27）

## 対象と方法

PR #38後のmainを基準に、受付・管理の機能一覧、状態遷移、永続化、同期、権限境界、印刷、障害時の動作を再確認した。検証手段はTypeScript検査、両アプリの本番ビルド、Reactによる画面操作テスト、fake-indexeddb、実際のFirebase SDKを接続したFirestoreエミュレータ、Functionsのエミュレータテスト。コードだけを眺めた項目と、実行して確認した項目を区別する。

本番イベントの受付、削除、初期化、端末の承認・権限変更は実行しない。公開ブラウザは未承認端末であり、承認後の管理・受付画面の操作は独立したテスト環境で確認する。iPad実機のカメラ・音量・Safari印刷ダイアログ・実際の用紙は、この環境からは検証できない。

## 今回修正した問題

| 領域 | 原因・変更 |
| --- | --- |
| イベント切替 | 遅れて返る設定・部員・分析・購読結果が別イベントへ混入しないよう、古い処理を無効化。切替時に関連モーダル・データをクリアする。 |
| 同一イベントの再選択 | 同じイベントを選ぶと一覧と公開情報だけが消える問題を修正。 |
| 起動時の設定 | サーバー設定を読む前のデフォルト値の書き込みを防止。読み込み中のユーザー編集も保持する。 |
| ストレージ障害 | キャッシュ保存の容量不足でアプリ全体が落ちないよう例外処理。破損した設定・デザイン・履歴の読み込みを補強。 |
| 意図しない削除 | 起動するだけでDEMO-2027を削除する旧処理を撤去。 |
| イベント作成・公開・状態変更 | 保存成功前に確定済みの表示へ進まない。状態だけを更新して他端末の新しい設定や版数を巻き戻さない。イベントIDの直接編集を防止。 |
| 公開処理 | 保存済み一覧を正本とし、古い画面のチケットを削除後に再作成しない。公開切替をトランザクション化し、在庫版数・発行済み番号などを古い画面の値で上書きしない。開催中の再公開で準備中へ戻さない。 |
| チケット発行 | 既存一覧の全保存をやめ、新規分だけを追加。発行番号の競合を検出し、既存の受付状態を保持する。番号変更後の内部ID衝突・安全な整数範囲も考慮。 |
| チケット変更・削除 | 本体・公開件数・データ版数を同一トランザクションで更新。削除と編集の競合でも件数が食い違わない。 |
| 終了・別イベントへの公開切替 | オフライン端末の古い未送信0件では終了しない。受付がサーバー時刻で報告した、対象イベント・停止・未送信0件の新しい情報を確認する。未回収なら待機する。 |
| 管理と受付を同時に開く運用 | 管理側のハートビートや名前変更が受付の未送信件数・モードを上書きしない。管理側の通信で受付の確認時刻を更新しない。 |
| 受付の保存 | 同一端末内の複数画面が同じ未使用チケットを同時に受け付けないよう、読み込み時点の状態を保存トランザクションで照合。新規サーバーチケットを受け付けた場合、再起動用の端末内件数も更新する。 |
| 同期キュー | DB v8で並び順の索引を追加し、毎回全履歴を走査しない。未同期状態だけを取得し、時計の巻き戻りでも受付順を保持。v7からの移行時に履歴を削除しない。 |
| 不安定な通信 | 最新チケットのサーバー読み込みに1.5秒の上限を設定。読み込みだけを中断扱いにし、保存済みのオフライン一覧で従来の判定を継続できるようにした。 |
| カメラ復旧・停止 | カメラ起動失敗後の再起動操作と、保存を中断せず準備画面へ戻る停止操作を追加。 |
| 音声 | 音声エンジンの準備通知とタイマーが重なっても二重読み上げしない。以前の受付の遅延読み上げを無効化。管理画面の音量・成功音・音声案内設定を同じ端末の受付で参照する。旧WAVのバイト列は維持。 |
| デザイン保存 | 名前ではなくイベントIDで保存し、同名イベントの混同や改名後の消失を防止。旧来の名前キーからは保存時に移行。背景画像の遅れた読み込みで新しい背景やリセットを上書きしない。 |
| バックアップ復元 | 画面だけの変更で成功と表示せず、形式検証後に不足データをFirebaseへ保存する。既存イベント・チケット・受付状態は上書きしない。形式・通信失敗は成功扱いにしない。 |
| 出力・入力 | CSVで数式として解釈される文字列をエスケープ。日付の初期値を端末のローカル日付に統一。イベントIDの乱数部分を拡張。端末名の連続変更を直列化し、登録の連打・長さを検証する。 |
| Firebaseルール | 受付自身の停止報告は対象端末の所有関係・型・長さ・サーバー時刻を検証。古い受付記録の再利用によるチケット単独更新を拒否。受付時刻・記録IDの形式と長さを制限。承認・役割・所有者の保護は維持。 |
| Functionsのソース | イベント削除時に過去の公開トークンも削除。全初期化で、親文書がないサブコレクションも対象にする。いずれもエミュレータのデータだけで検証。 |

## 本番反映の範囲

通常の受付・管理はFirestore SDKとルールで動作する。PagesとSpark対応ルールの既存ワークフローで本番に反映し、配信ファイルとRules APIのデプロイ結果を確認する。Functions側の修正はソースとエミュレータ検証までであり、Functions本番の配置・料金プラン・初期化Callableの実動作確認を完了したとは扱わない。Functionsの全消去を本番で試さない。

IndexedDB v8には履歴を残す移行が含まれる。運用前にオンラインで両アプリを再読み込みし、受付端末で対象イベントの停止・未送信0件の最新報告を送ってから終了/イベント切替を行う。

## 残る制約・実機で必要な確認

1. 完全にオフラインの独立した端末間では入退場状態を共有できない。同じQRの別端末での重複使用や、別の入口端末だけが持つ入場記録を出口で照合することは、この構成だけでは保証できない。存在しない入場記録を捏造して通す修正は行わない。同一端末での入口/出口切替か、別途通信・状態引き継ぎの設計が必要。
2. iPad/Safariのカメラ許可、画角、実際の読み取り速度、音量、スリープ復帰、長時間稼働、AirPrintの用紙と改ページは実機未検証。DOMテストを実機印刷の保証とは扱わない。
3. 本番ブラウザの承認済み端末操作、実データの完全性、Functionsの本番配置は未確認。テスト用の承認を本番に作らない。
4. 管理権限者が既存データを直接変更した場合、以前の版で不整合になった件数・失効済みイベントの未送信記録などを、根拠なく自動書き換えしない。端末内記録は保持する。
5. 既存の名前だけで保存された同名イベントのデザインは、過去の保存先が既に共通なので自動分離はできない。ID別に保存し直した後は独立する。
6. 管理用バックアップは設定・イベント概要・チケット・部員・分析スナップショットの不足分復元用。端末承認、秘密の公開トークン、受付の生履歴をファイルから権限付きで再投入する機能ではない。
