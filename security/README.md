# 隔離環境での攻撃・防御検証（2026-11-06）

基準は `c88322dbe12670fbd55b26f160786ec973582296`（PR #78 の修正）。攻撃側2担当、防御側2担当、独立レビュー担当に分け、再現できた問題を修正し、同じテストで再攻撃した。本番データへの攻撃・負荷送信・権限変更・デプロイは行っていない。

## 実行方法と隔離の境界

依存関係をインストール後、Node.js 22とJava 21の環境で実行する。

```sh
npm install
npm install --prefix functions
npm run test:security
```

専用runnerは本番用認証ファイル・トークン・Firebase設定を引き継がず、Firestoreを `127.0.0.1:8080`、プロジェクトを `demo-qr-*` に固定する。テストsuiteはSDKやfixtureの読込前に接続先と設定を検査する。任意のコマンドやデプロイ引数は受け付けない。通常実行では、修正前ソースを読む再現用環境変数も除去する。

エミュレータ設定は [firebase.security.json](../firebase.security.json)。サービスはloopbackで待ち受け、攻撃テストごとにdemoプロジェクトを分ける。これは本番と分離したテスト環境であり、任意の悪意あるテストコード自体を封じ込めるOSサンドボックスの提供を意味しない。

試験は単発200KB以下の入力、少数回の権限操作、圧縮データ1件の2MB展開上限検査に限定した。大量送信や外部サービスへの攻撃は含まない。

## 再現した問題と対策

| 攻撃側の試み | 修正前の結果 | 防御後 |
|---|---|---|
| 解除済みinstallationのowner UIDでheartbeatを送る | 許可された | ownerの有効性とinstallationの現在の承認を双方確認 |
| ownerを無効化・削除した後、古いinstallationでheartbeatを送る | 許可された | 拒否。承認済み引継ぎ受付の通常更新は維持 |
| 申請・heartbeat・登録解除の日時欄に200KBを保存 | ルールの複数経路で許可された | 共通の1〜40文字の検証を作成・更新・解除経路に適用 |
| Functionsの解除済み管理端末で名称更新 | 許可された | UID・端末・承認済みinstallationを同一transactionで確認 |
| Functionsの受付・エラーログへ巨大な日時文字列を保存 | Date.parseが受理すれば許可された | ISO形式と20〜40文字を検証。過去の正規オフライン日時は維持 |
| 自作のオフラインQRで別イベントの承認を省略 | 端末内の受付データとして保存された | その端末の承認済みeventIdとの一致を必須化 |
| eventIdのない旧承認キャッシュから受付を復元 | 未指定イベントでも復元できた | キャッシュ読込・復元・状態遷移でもイベント一致を必須化 |

未認証の一覧取得、所有者・grantの偽造、自己承認、副管理者の昇格、他イベントのチケット読取、受付リプレイ、不正スキーマ・パス、QRの過大入力と解凍上限、バックアップによる権限・プロトタイプキーの持込みも有限fixtureで検査した。これらの検証は、今回確認した特定の経路を対象とする。

## 運用上の影響と残る課題

- イベントIDがない旧承認キャッシュの端末は、オンラインでイベントごとの承認を確認し直す必要がある。明示的に承認済みの同一イベントでは、従来のオフライン転送と受付を維持する。
- 同一イベントの転送QRには発行元の電子署名がない。ハッシュは発行元を証明しないため、管理者の画面から直接読み取る物理的な信頼が必要。取り込み画面を操作できる人による同一イベントの偽データ持込みは、今回のイベント一致だけでは解決していない。
- 同じ匿名UIDから2件のpending申請が作れることを確認した。自己承認は拒否されるが、申請数のサーバー側制限は未実装。別UIDの量産も含めた受付制限・監視は別途必要であり、この残留確認を「攻撃を防げた」とは数えない。
- 通信断中の即時権限失効、本格的なDoS/DDoS、Google Cloud IAM・課金上限・App Check・HTTPS transportの防御は今回実測していない。FunctionsはエミュレータDBに対してhandlerを直接呼び出して検証した未公開コードである。
- 管理者権限を持つ端末からの全データスキーマの厳格化、実iPadのカメラ・音声・紙印刷は検証範囲外。

今回のSecurity Rules変更は、上記の所有権・承認状態・入力上限を守るための対策案を隔離検証したもの。本番へ広く公開する前には、適用する差分のレビューと実機確認が必要であり、攻撃全般に対する安全性を保証するものではない。
